# Changelog

All notable changes to this project are documented in this file.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- `depper host init ADMIN@HOST [REPO]` prepares a fresh Debian/Ubuntu or Fedora/RHEL host over SSH, as root or a user with passwordless sudo. It pins the host key after you confirm its fingerprint (default file `REPO/.depper/known_hosts`, mode 600), creates an unprivileged deploy user with your public key, enables lingering and starts its systemd user manager, installs `rsync` and the container engine the configuration uses, runs `depper doctor` as the deploy user, and writes `host`, `user`, `port`, `known_hosts`, and `identity_file` into `[deploy]` (or `[targets.NAME]`) with a minimal edit that keeps comments. Every step is checked first, so a second run changes nothing. It prints the plan and asks before applying; `--dry-run` changes nothing, and `--yes` skips the questions (required without a terminal).
- Opt-in options for `host init`: `--harden-ssh` (a `10-depper.conf` sshd drop-in that disables password and keyboard-interactive login, validated with `sshd -t` and `sshd -T` and by new logins before and after the reload; guarded, see below), `--firewall PORTS` (ufw or firewalld; guarded; the `--port` value and every port sshd listens on are always included), `--auto-updates` (unattended-upgrades or dnf-automatic), `--tailscale-authkey-env NAME` (installs Tailscale; the key is read from the environment and never appears in a command line, output, or the host record), `--cloudflared`, and `--container podman|docker|none`. Also `--user`, `--port`, `--identity`, `--key`, `--known-hosts`, and `--no-write-config`.
- Guarded `--harden-ssh` and `--firewall`: before the change, `host init` arms a transient systemd timer on the host (`depper-ssh-revert`, `depper-firewall-revert`, 120 s) that undoes it by itself, and disarms it only after a new deploy-user login and a new administrator login succeed. A failed check rolls back at once, or through the timer when the administrator connection is gone, and the error says what happened; a failed disarm is reported loudly (including which marker files to remove to keep the change); an interrupted run is undone by the timer, and the next `host init` finishes it first ("Finishing an interrupted host init": it starts the revert if the timer is waiting, waits for a running revert, then runs the remaining revert itself; a dry run only warns). Each guard keeps its state in `/var/lib/depper/guard/<unit>/` (`revert.sh` and explicit markers). `revert.sh` takes who runs it (`timer`, `boot`, `pending`, `now`) and holds a lock; disarm takes the same lock and writes a `disarmed` marker, after which a timer or boot revert does nothing, and a started revert is reported as undone. Each undo step removes its marker only if it succeeded; otherwise the script exits 1 without writing `reverted` and the timer or next host init retries. The sshd reload happens always for timer, boot and pending, and for a rollback only if sshd was reloaded. `depper-guard-revert.service` (enabled when a guard is armed, kept installed) runs every guard's revert at boot, because transient timers do not survive a reboot. On firewalld the zone is determined when the revert is armed and recorded (`zone`) for both the step and the revert; ports added offline are removed with `firewall-offline-cmd`, and a firewalld that was enabled but not running is only stopped again (`was-enabled`). The timer is armed with `systemd-run --collect` (`Type=oneshot`, `AccuracySec=1s`, `RandomizedDelaySec=0`) and `host init` prints the exact time it fires. After a lockout `host init` polls the host for the `reverted` marker and reports when the timer reverted the change, or that the revert is overdue and to use the provider console. `systemd-run` and systemd 236 or later are required on the host only when a guarded step changes something.
- `host init --host-key-fingerprint SHA256:...` (repeatable) pins only scanned keys that match and refuses when none does. `--yes` now refuses to pin an unverified host key unless `--host-key-fingerprint` or `--trust-on-first-use` is given (or the key is already pinned).
- `host init` installs a compose provider when `[container].compose` is used: `podman-compose` for podman, the first available of `docker-compose-plugin`, `docker-compose-v2`, and `docker-compose` (version 2 or later) for docker, and refuses with a clear message when none is available. `depper doctor` gains a `compose` check that runs `<engine> compose version` in compose mode.
- `host init` on Amazon Linux 2023 and later (Amazon Linux 2 is refused): docker uses the `docker` package, Tailscale uses Tailscale's Amazon Linux repository, and podman is refused with a message.
- `host init` and `host status` on Arch Linux and its derivatives (`ID=arch`, or `arch` in `ID_LIKE`: Manjaro, EndeavourOS, CachyOS, Omarchy, ...); the plan names the detected `ID` and family. Packages come from `pacman -S --needed --noconfirm` only when the local sync database has every one of them (checked with `pacman -Si`, installed packages with `pacman -Q`); otherwise host init refuses before changing anything and asks you to run `sudo pacman -Syu` yourself. depper never runs `pacman -Sy` or `-Syu`. podman installs `podman`, `shadow`, and `passt` (or `slirp4netns`); docker installs `docker`; compose uses `podman-compose` or `docker-compose`; `cloudflared` and `tailscale` come from the official repositories. `--auto-updates` is refused on Arch. `--firewall` uses an active ufw, else a running firewalld, else installs ufw, enables `ufw.service` at boot as part of the guarded step (the revert disables it again; new marker `enabled-unit`), and refuses when an active `nftables.service`, `iptables.service`, or `ip6tables.service` has a non-empty ruleset or when firewalld is enabled but stopped. `host status` warns when ufw is enabled but `ufw.service` is not.
- `--harden-ssh` reloads the active `ssh.service` or `sshd.service`, preferring the one the facts found, and accepts socket-activated sshd (`ssh.socket` or `sshd.socket` without a running service) with no reload, in the step and in the revert; `--firewall` also allows the ports of an active `sshd.socket`.
- The refusal of an administrator whose `sudo` needs a password now names both ways forward: root login with an SSH key, or a temporary `NOPASSWD` sudoers line to remove after host init.
- `depper host status` shows a `ssh match blocks` warning when a `Match` block in the sshd configuration sets password, keyboard-interactive, challenge-response, or root login.
- `/etc/depper/host.json`, a root-owned, secret-free record of what `host init` set up (version, deploy user, engine, applied steps, installed packages, hardening).
- `depper host status [REPO]` reads that record and the live state as the deploy user and reports `pass`, `warn`, `fail`, or `info` per check, with `--json` output; exit status 1 when a check fails.
- `depper init` detects the project type and pre-fills `depper.toml`. Detectors, in precedence order: Docker Compose, Dockerfile, Go, Node.js, Python, Rust, static site, with a generic template as the fallback. Inferred lines carry a comment naming their source, and warnings and server requirements appear in the header. `--print` writes the configuration to standard output, `--force` replaces an existing `depper.toml`, and `--json` reports the detection. Nothing in the repository is executed and `.env` files are not read.
- `.github/workflows/e2e.yml`, an end-to-end test on a real Ubuntu runner that exercises `host init`, deploy, rollback, secrets, locks, `ssh -W` health checks, podman (build, image, and compose modes), SSH hardening, and ufw. It runs on pushes to `main` and `feature/**` and on `workflow_dispatch`.
- Documentation: `docs/hosts.md` starts with `host init`, hardening, `host status`, and a support status note; the manual steps follow.

### Changed

- `depper init` now overwrites an existing `depper.toml` only with `--force`, and still refuses when a `deploy.toml` exists. Container projects get `engine = "podman"`.
- Compose validation runs `compose config` with its output discarded instead of `compose config --quiet`, which podman-compose (the provider of `podman compose` on Ubuntu 24.04) does not accept.
- Remote scripts no longer trust an inherited `XDG_RUNTIME_DIR` that the deploy user does not own, and keep `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_CACHE_HOME`, and `XDG_STATE_HOME` only when the directory is owned by the deploy user and not writable by group or others (or is missing and its parent meets that test; symbolic links are followed), and drop them otherwise. The process-mode start script (`.depper-start.sh`) and every container engine invocation in generated units (`ExecStart`, `ExecStartPre`, `ExecStop`, through `/bin/sh -c`) apply the same sanitising, so services no longer inherit a foreign `XDG_*` from the user manager. depper cannot change what the systemd user manager itself inherits; on hosts whose `/etc/environment` sets another user's XDG directories, remove those lines (see [Preparing a host](docs/hosts.md#another-users-xdg-variables-in-etcenvironment)).
- `host init` writes `depper.toml` only after `depper doctor` passes; when it fails, the edit is printed and the file is left alone. The file is re-read before writing (`depper.toml changed while host init was running` aborts), the edited file must resolve to exactly the intended connection with nothing else changed and every other target unchanged, `port` is also written when the key exists or a target would inherit another port, `identity_file` is set when the table already sets one (the private key of the authorized public key, or `host init` refuses and suggests `--key`), the editor no longer mistakes `"""` or `'''` inside strings and comments for multi-line delimiters, and writes follow symbolic links (`depper.toml`, `known_hosts`).
- `host init --firewall` also allows every sshd `Port` and `ListenAddress` port and the `ListenStream` ports of an active `ssh.socket`, warns when `--port` is not one of them, and on firewalld opens the ports in the zone of the interface the administrator connection arrives on (default zone with a warning), in the runtime and permanent configuration without a reload. The firewall and sshd hardening now run after the other steps.
- `host init --harden-ssh` never weakens `PermitRootLogin`: the value is read without depper's own drop-in (`sshd -T` on a temporary copy of the configuration without `10-depper.conf`), and the drop-in sets `prohibit-password` only when that value is `yes`; otherwise the directive is omitted, and a line written by earlier builds over a stricter setting is removed again. Match blocks that set the hardened options are reported as a warning in the plan and are not refused.
- `host init` handles `authorized_keys` more carefully: commented lines are ignored, and a key that is present only on a line with options (`command=`, `from=`, `restrict`, ...) is reported as restricted; an unrestricted line is added only with an explicit `--key`. A deploy user whose password field is `!` or `!!` gets `usermod -p '*'` when sshd has `UsePAM no`, and a `nologin`/`false` shell is fixed with `usermod -s /bin/sh` only when `host.json` says depper created the user (otherwise a warning).
- Every ssh connection `host init` opens passes `-o ForwardAgent=no -o ForwardX11=no -o ClearAllForwardings=yes`. The Tailscale auth key file is removed by a trap on `EXIT`, `HUP`, `INT`, and `TERM`, and `tailscale up` runs under `timeout 120`.
- `depper host status` checks the effective `sshd -T` values (run as the deploy user with a throwaway host key and the session's connection spec, so `Match` blocks apply) instead of only the drop-in file; when `sshd -T` cannot be read as the deploy user, it probes the methods sshd offers to new connections instead. A feature recorded in `host.json` but not in effect now is a warning, not a failure.
- `host.json` `steps` also lists `known-hosts`, `config`, and `record`. The record is written after the configuration, and also after a failed doctor run or a failed apply.
- `.depper/` is now in the always-excluded rsync patterns, so `.depper/known_hosts` is never shipped in a release (the default exclude is anchored as `/.depper/`, so only the top-level directory is excluded).
- Editing `depper.toml` parses table headers with a proper tokenizer, so quoted keys that contain `]` and trailing comments are handled.
- The README quick start is now `depper init`, `depper host init root@SERVER`, `depper deploy`; the manual path is documented in `docs/hosts.md`.

### Fixed

- podman compose silently ran docker's compose plugin: with docker installed, `podman compose` runs `docker-compose` as its provider, which talks to the deploy user's podman API socket, so a compose deploy failed with `failed to connect to the docker API at unix:///run/user/UID/podman/podman.sock` while `depper doctor` passed. A podman compose deploy now enables and starts `podman.socket` for the deploy user before any compose command (idempotent, whatever the provider). The doctor `compose` check now names the provider podman runs and, for docker-compose, fails when `podman.socket` is masked or not found (with the fix command) and warns when it is only disabled (the next deploy enables it). `host init` no longer refuses podman compose when `podman-compose` cannot be installed but a docker-compose plugin or binary is present: it accepts that provider, plans `Enable podman.socket for USER`, and records it in `host.json` (`compose_provider`, `enabled_units`).
- Services could lack the `docker` group: a systemd user manager started before the deploy user joined `docker` (from an earlier run, or by lingering in the same run) keeps its old groups, so the unit's `docker run` failed with `permission denied` on `/var/run/docker.sock` while `docker build` over SSH worked. `host init` now adds the group before enabling lingering, and when the manager is already running without the group it restarts `user@UID.service` (the plan says this restarts all of the user's services) and checks the group in `/proc/<pid>/status`. `host status` and `depper doctor` gain a `docker group` check (`service manager lacks docker group`).
- `host init` no longer enables `docker.service` on a socket-activated host. Docker counts as enabled when `docker.socket` is enabled or `docker.service` is enabled or running; otherwise `host init` enables `docker.socket` where it exists, else `docker.service`, and records the unit in `host.json` (`enabled_units`).
- A compose service now survives an unclean stop. When the user manager was restarted abruptly, conmon was killed while podman still listed the container as running with no port forwarding; the next start's `compose down` failed and `compose up` reused the stale container, so health failed and `depper restart` did not recover. Compose units now run an `ExecStartPre=-` cleanup (`compose down --remove-orphans`, then `rm -f` of every container still labelled `com.docker.compose.project=<project>`), start with `up --build --remove-orphans --force-recreate`, and fall back to the same label-based `rm -f` in `ExecStop` when `compose down` fails. podman compose units also get `Wants=podman.socket` and `After=podman.socket`. `depper restart`, `secrets push`, and `rollback` restart the unit and get the same behaviour.
- A failed apply step no longer prints the host's error twice (for example pacman's `pacman could not install ...`): the message is shown once as it happens, and the final error refers to it. The `--json` report still includes it.

### Support status

`host init` has been verified on a real Ubuntu 24.04 host only: `openssh-server` and `ssh.socket` reload, apt packages, `useradd`, lingering, subordinate ids, sshd hardening and ufw, `ssh -W` health checks, rsync, podman in build, image, and compose modes, and secrets push, rollback, and unlock. Fedora/RHEL (`dnf`, `firewalld`, `dnf-automatic`), Arch Linux (`pacman`, ufw with `ufw.service`, `sshd.service`), Tailscale, `cloudflared` installation, the docker engine, a `sudo` administrator, SSH ports other than 22, and IPv6 have not been tested on real hosts.

## [0.2.0] - 2026-10-13

The tool is renamed from `deployer` to `depper` and rewritten in Go as a single binary. Local requirements are `ssh` and `rsync`; Python is no longer needed on either side.

### Added

- Single static binary, published for Linux and macOS (amd64 and arm64) with SHA-256 checksums through GoReleaser.
- `install.sh`, a POSIX sh installer that detects OS and architecture, verifies the SHA-256 checksum, and installs to `/usr/local/bin` or `~/.local/bin` without `sudo`. `DEPPER_VERSION` and `DEPPER_INSTALL_DIR` select the version and directory.
- MIT license (`LICENSE`).
- README sections for installation, shell completion, updating, and uninstalling.
- Container services: `[container]` with docker or podman in `build`, `image`, or `compose` mode, including ports, volumes, extra run arguments, and a command override (`ports`, `volumes`, `args`, and `command` are rejected with `compose`). In build and image mode each release runs its own image tag, `depper/<name>:<release-id>`: image mode tags the pulled image, so a release keeps running the exact image it was deployed with, and records `image` and `image_digest` in the release metadata. Build-mode images carry the label `depper.service=<name>`, and pruning removes only images of its own service. The lowercased service name must be a valid image name.
- `[endpoint]` to record where a service is reachable without a tunnel.
- `[health]` with URL or command checks, `expect_status`, `timeout`, `start_period`, and `interval`. URL checks run from the host's network view over `ssh -W` (with `ControlPath=none` and a `LocalCommand` ready marker), with a remote `curl` fallback when forwarding is refused. `timeout` covers only the HTTP exchange; the SSH connection gets `max(15 s, timeout)`. A health command that exits with status 255 is reported as unhealthy, not as an ssh failure.
- `depper health` with `--watch` and `--count`, and `depper status`, both with stable `--json` output. Exit status 2 for an unhealthy service.
- Targets: `[targets.<name>]` overlays selected with `--target` or `DEPPER_TARGET`.
- `source = "git"` and `depper deploy --ref REF` to ship committed content with `git archive`.
- Release metadata (`.depper-release.json`), `depper releases`, pruning to `keep_releases` (default 5) including transaction backups and container images, and `depper rollback --to`.
- Release ids of the form `release-YYYYMMDDTHHMMSS.mmmZ-<hex>` (millisecond timestamp). Ordering uses the timestamp and never the random suffix. Older second-resolution ids remain valid, including for `rollback --to`.
- `depper check`: compares the deployed commit and secrets with the local repository; exit status 3 when the deployment is outdated, nothing is deployed, or secrets drift. `depper status` exits 0 whenever it could read the host, even if the service is unhealthy.
- Secrets management: `--env-stdin`, `depper secrets list`, `diff`, and `push`, backed by a per-deployment salt and HMAC-SHA256 fingerprints in an environment manifest. Values are never printed or read back from the host.
- `depper doctor` to check SSH, rsync, `sha256sum`, the systemd user manager, linger, disk space, the container engine, `cloudflared`, locks, and layout.
- `depper ci init` to generate a GitHub Actions workflow with per-target concurrency, a checksum-verified depper install, and secrets passed through `DEPPER_SSH_KEY`, `DEPPER_KNOWN_HOSTS`, and `DEPPER_ENV`. `DEPPER_SSH_KEY_FILE` and `DEPPER_KNOWN_HOSTS_FILE` override `identity_file` and `known_hosts`.
- A holder-aware lock: its `info` file carries a random ownership token (not shown in JSON output), an operation releases only its own lock, and `depper unlock` removes only the lock it inspected and fails if the lock changed hands. A lock is stale when it has not been refreshed for 15 minutes by the host's clock; running operations refresh it, and `depper unlock` removes a more recent lock only with `--force`. `age_seconds` in `unlock --json` is the time since the last refresh, and `depper doctor` reports "last refreshed X ago".
- `depper migrate` to convert deployments made by the Python `deployer`, with `--dry-run`. For default paths it leaves the relative compatibility symlink `~/.local/share/deployer/<name> -> ../depper/<name>`. It is resumable: rerun `depper migrate` after an interruption (the dry run says "resume the interrupted migration"). If it fails early, while the legacy metadata and unit still exist, it restarts the legacy units. Other commands report an interrupted migration, and `depper doctor` shows layout `migrating`. When a depper layout and a legacy layout both exist, every command that changes the deployment refuses and read-only commands warn.
- SSH options `user`, `port`, `identity_file`, and `known_hosts` (host key pinning with strict checking); IPv6 hosts.
- Automatic restore recovery guidance: after a failed restore the error lists the recovery steps, and `depper rollback` with no arguments restores the pre-operation state of the newest interrupted deploy, rollback, or secrets push, reported as `restored_transaction` in `rollback --json`.
- Ctrl-C and SIGTERM handling: the running `ssh` or `rsync` gets 2 seconds before it is killed, then cleanup runs and the lock is released. A deploy interrupted this way leaves its release marked discarded (`discarded: true` in `releases --json`), and the next successful deploy prunes it.
- `--json` output for every command that reports a result, with human messages moved to stderr.
- Documentation under `docs/` and Go-era examples under `examples/`.

### Changed

- Command, files, and host names: `depper`, `depper.toml` (`deploy.toml` is still read), `~/.local/share/depper/<name>`, `.depper/`, `depper-<name>.service`, and `depper-tunnel@<name>.service`.
- `current` and `previous` links are relative, so a deployment directory can be relocated.
- Old releases are pruned after a successful deploy; the Python tool kept all of them.
- The remote base path (`[deploy].path`, or the default under the remote `$HOME`) may contain only letters, digits, and `. _ @ + / -` (`^/[A-Za-z0-9._@+/-]+$`). A remote `$HOME` with other characters needs `[deploy].path`. `identity_file`, `known_hosts`, `DEPPER_SSH_KEY_FILE`, and `DEPPER_KNOWN_HOSTS_FILE` may not contain whitespace.
- Remote scripts run with `ssh -T` and are sent wrapped in one group, so the remote shell parses each script in full before running any of it.
- `[tunnel]` cannot be overridden per target.
- A deployment's transaction is recorded per release, and a release's applied environment and unit are retained so `rollback --to` restores exactly what that release ran.
- Container modes have no `container.env` file. In build and image mode the values come from the unit's `EnvironmentFile` and are passed with `--env KEY`; the key list is kept in the reserved variable `DEPPER_CONTAINER_ENV_ARGS`. Multi-line and quoted values are allowed; a value over 60 KiB is rejected, and the error names the key only. In compose mode every compose command runs with `--env-file /dev/null`, so a `.env` file in the repository or release is ignored, and `${VAR}` comes from depper's environment: the unit's `EnvironmentFile` at runtime and exported values during setup. Existing container deployments must run `depper deploy` once before `depper secrets push`.

### Security

- Secret values are never placed in command lines, rsync transfers, or output; uploads are atomic and private (modes 600 and 700), and symlinked metadata paths are refused.
- Old environment values are removed with the release that retained them when it is pruned.

## [0.1.0] - not tagged

Initial release of the Python tool `deployer`.

### Added

- `deploy.toml` configuration with `[service]`, `[deploy]`, `[env]`, `[secrets]`, and `[tunnel]`.
- Deployment of a repository to a Linux host over SSH and rsync as a systemd user service, with release directories, `current` and `previous` links, optional setup commands, and a health command.
- Automatic restore of the previous release when a deployment fails to start.
- `status`, `logs`, `restart`, `stop`, `rollback`, and `init` commands.
- Dotenv secrets (`[secrets].file` and `--env FILE`) stored in a private environment file on the host and never uploaded with the release.
- Optional Cloudflare Tunnel support with an owned tunnel per service and `tunnel`, `tunnel-status`, `tunnel-logs`, and `tunnel-stop` commands.
- Per-service deployment lock.
