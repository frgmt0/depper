# CI/CD

depper runs the same way in CI as on a workstation: it needs the binary, an SSH key, and the host key. `depper ci init` generates a GitHub Actions workflow that does this. Other CI systems can follow the same steps.

## depper ci init

```sh
depper ci init                       # deploy on pushes to main
depper ci init --branch production
depper --target production ci init   # deploy the production target
depper ci init --force               # overwrite an existing workflow
```

The command reads `depper.toml` (so it needs a valid configuration, and a target if the file defines targets and no base host), writes `.github/workflows/depper.yml`, and prints the repository secrets you need to create. It refuses to overwrite an existing workflow without `--force`. Flags: `--branch` (default `main`), `--force`, and the global `--target`. It does not commit or push anything.

## The generated workflow

```yaml
# Generated by `depper ci init`. Re-run it with --force to regenerate.
name: depper deploy

on:
  push:
    branches: ["main"]
  workflow_dispatch:

concurrency:
  group: depper-production
  cancel-in-progress: false

permissions:
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - name: Install depper
        ...
      - name: Configure SSH
        ...
      - name: Deploy
        env:
          DEPPER_ENV: ${{ secrets.DEPPER_ENV }}
        run: printf '%s' "$DEPPER_ENV" | depper deploy --target production --env-stdin

      - name: Health check
        run: depper health --target production
```

How each part works:

- **Trigger.** A push to the chosen branch, or a manual run (`workflow_dispatch`).
- **Concurrency.** One group per target (`depper-<target>`, or `depper-default` without a target) with `cancel-in-progress: false`. A second push waits for the running deployment instead of cancelling it, because cancelling a deployment mid-way is worse than waiting. depper's own host-side lock is a second line of defence.
- **Permissions.** `contents: read` is all the job needs: it checks out the repository and talks to your host over SSH. Deployment does not use the GitHub token.
- **Checkout.** `fetch-depth: 0` gives full history so release metadata can record the commit and ref.
- **Install depper.**
  - When the depper that generated the workflow is a release build (for example `v0.2.0`), the workflow pins that version: it downloads `depper_<version>_linux_amd64.tar.gz` and `checksums.txt` from the GitHub release, verifies the archive with `sha256sum -c --ignore-missing`, and extracts the binary onto `PATH`. Regenerate the workflow to change the pinned version.
  - When depper was built without a release version (`dev`, as with `go install ...@latest`), the workflow uses `actions/setup-go` and `go install github.com/frgmt0/depper/cmd/depper@main`, which tracks the main branch and is not pinned.
- **Configure SSH.** Writes the secrets `DEPPER_SSH_KEY` and `DEPPER_KNOWN_HOSTS` to files under `$RUNNER_TEMP` with `umask 077`, and exports their paths as `DEPPER_SSH_KEY_FILE` and `DEPPER_KNOWN_HOSTS_FILE`. These variables override `identity_file` and `known_hosts` from `depper.toml`; see [Configuration](configuration.md#environment-overrides-for-credentials). Their paths may not contain whitespace, which also applies to the temporary files you create on other CI systems.
- **Deploy.** If the configuration has `[secrets]` for the selected target, the dotenv content is taken from the secret `DEPPER_ENV` and passed on standard input with `--env-stdin`, so no secrets file is needed on the runner and nothing is written to disk. Without `[secrets]`, the step is just `depper deploy`.
- **Health check.** Generated only when `[health]` is configured; runs `depper health`, which exits 2 if the service is unhealthy. `depper deploy` already waits for health and rolls back on failure, so this step confirms the final state.

## Repository secrets

`depper ci init` prints this list for your configuration. Create the secrets under Settings, Secrets and variables, Actions.

| Secret | Content |
| --- | --- |
| `DEPPER_SSH_KEY` | Private key that can log in to the deploy host. Use a dedicated key without a passphrase, installed only for the deploy account. |
| `DEPPER_KNOWN_HOSTS` | One or more host key lines for the host. |
| `DEPPER_ENV` | The dotenv content of `[secrets].file`. Only needed when `[secrets]` is configured. |

```sh
gh secret set DEPPER_SSH_KEY < ~/.ssh/id_ed25519_ci
ssh-keyscan -p 22 203.0.113.10 | gh secret set DEPPER_KNOWN_HOSTS
gh secret set DEPPER_ENV < .env.production
```

### known_hosts

The workflow always sets `known_hosts`, so ssh runs with `StrictHostKeyChecking=yes` and accepts only the keys in the secret. There is no "accept new host" fallback: a changed host key fails the deployment.

`ssh-keyscan` retrieves whatever key the network returns, so verify the printed fingerprint against a trusted source (the provider console, or `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` on the host) before saving it. The entry must match the `host` in the configuration: an entry for `203.0.113.10` does not match a DNS name for the same machine. Use the same host string the workflow will use.

### The host must be reachable from the runner

The runner has no `~/.ssh/config`, so an SSH alias in `[deploy].host` will not resolve there. Define a [target](configuration.md#targets) with a real address and generate the workflow for it:

```toml
[targets.production]
host = "deploy@203.0.113.10"
```

```sh
depper --target production ci init
```

GitHub-hosted runners must be able to reach that address on the SSH port. A host that is only reachable over Tailscale or a VPN needs a self-hosted runner on that network, or a step that joins the network; depper does not do that.

## Targets

`depper ci init` always writes `.github/workflows/depper.yml`, so it produces one workflow per run. To deploy several targets, generate each one and rename the file before generating the next:

```sh
depper --target staging ci init --branch develop
mv .github/workflows/depper.yml .github/workflows/depper-staging.yml
depper --target production ci init --branch main
```

Edit the renamed file's `name:` if you want the two workflows distinguishable in the Actions UI. Concurrency groups are per target, so staging and production deployments do not block each other. Both workflows read the same secret names; when the targets use different keys, give each target its own GitHub environment with its own `DEPPER_SSH_KEY`, `DEPPER_KNOWN_HOSTS`, and `DEPPER_ENV` (add `environment: <name>` to the job), or edit the secret names in the copies.

## Security considerations

- Anyone who can push to the trigger branch, or edit the workflow, can run commands as the deploy account. Protect the branch, and consider a GitHub environment with required reviewers for production.
- The workflow runs on pushes only to the branch you chose. It does not run for pull requests from forks, which should not receive the secrets.
- The SSH key and `DEPPER_ENV` are written only to `$RUNNER_TEMP` (for the key) or streamed (for the dotenv content). GitHub masks secret values in logs, but multi-line secrets and derived values are masked less reliably; depper itself never prints values.
- The workflow uses the `main` or pinned release binary of depper. Pin releases in production.

## Using depper from other CI systems

The steps are the same everywhere:

1. Install `depper`, `ssh`, `rsync`, and `git` on the runner. Download a release binary and verify it against `checksums.txt` (see the [README](../README.md#install)).
2. Write the private key and the known_hosts content to files with restrictive permissions, outside the repository:

   ```sh
   umask 077
   printf '%s\n' "$DEPPER_SSH_KEY" > "$RUNNER_TEMP/id"
   printf '%s\n' "$DEPPER_KNOWN_HOSTS" > "$RUNNER_TEMP/known_hosts"
   export DEPPER_SSH_KEY_FILE="$RUNNER_TEMP/id" DEPPER_KNOWN_HOSTS_FILE="$RUNNER_TEMP/known_hosts"
   ```

3. Check out full history if you want commit metadata and `depper check` to work (`git fetch --unshallow` on shallow clones).
4. Deploy, passing secrets on standard input rather than writing them to disk:

   ```sh
   printf '%s' "$DEPPER_ENV" | depper deploy --target production --env-stdin
   depper health --target production
   ```

   `DEPPER_TARGET=production` can replace `--target`.
5. Serialize runs per target with the CI system's own concurrency control. If two depper operations on the same service overlap anyway, the second fails on the host lock.

Exit codes are stable and suitable for pipeline logic: 0 success, 1 error, 2 unhealthy, 3 drift or outdated. `depper check --target production` exits 3 when the deployed commit or secrets differ from the repository, or when nothing is deployed, which is useful as a scheduled drift check. Add `--json` for machine-readable output (human messages then go to stderr).

For a deployment that must run only after tests, make the deploy job depend on your test job in your own pipeline; the generated workflow does not run tests.
